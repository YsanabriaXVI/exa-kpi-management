 ## Dos tensiones que siguen abiertas

  ### “Reducir gasto administrativo x%”

  La referencia v4 lo considera un caso confiable:

  COMPARISON
  GREATER_IS_BETTER
  ABSOLUTE_VALUE
  Comparison Detected = YES

  Pero el contexto más reciente ordena tratarlo como ambiguo entre:

  Current expense
  → DIRECT_CURRENT_VALUE
  → LOWER_IS_BETTER

  y:

  Reduction achieved
  → ACHIEVED_CHANGE
  → GREATER_IS_BETTER

  Para futuros análisis aplicaré la decisión más reciente: debe quedar NEEDS_CONFIRMATION si no se indica baseline o forma de reporte.

  ### COMPARISON como Calculation Pattern

  La referencia incluye COMPARISON como patrón, pero también afirma que Calculation Pattern y comparación son independientes.

  Esto requiere una definición posterior. Por ahora entiendo que debemos preservar dos preguntas separadas:

  ¿Cómo se obtiene el valor actual?
  DIRECT / DERIVED / MULTI_INPUT / COMPOSITE

  ¿Debe compararse contra un baseline?
  NO / SAME_PERIOD_PREVIOUS_YEAR / PREVIOUS_PERIOD / CUSTOM

  Un caso puramente comparativo podría seguir recibiendo la etiqueta de referencia COMPARISON, pero no asumiré todavía que sea un tipo físico exclusivo.

  ## Criterio que usaré en adelante

  Cuando haya diferencias entre fuentes:

  1. Decisiones explícitas más recientes del usuario.
  2. Principios arquitectónicos acordados.
  3. Casos confiables del archivo v4.
  4. Casos ambiguos del archivo v4.
  5. Fixtures sintéticos, únicamente como pruebas.
  6. Nunca convertir automáticamente una inferencia en decisión persistida.

  Este archivo queda entendido como la base fundamental para Definition Assist, clasificación, preguntas y fixtures, pero no resuelve todavía la fórmula oficial de Compliance
  comparativo ni los modelos físicos de snapshots, baselines o mappings.

• # Reporte de entendimiento del dominio KPI

  ## 1. Aspectos que quedaron muy claros

  ### Separación de responsabilidades

  El flujo conceptual está definido así:

  KPI Definition
  → KPI Configuration
  → KPI Pool
  → Scorecard
  → FINALIZED
  → Frozen Snapshot
  → Monitoring Results
  → Evaluation
  → Reports

  Cada dominio tiene responsabilidades distintas y no debe absorber funciones de los demás.

  ### KPI Definition

  Representa el concepto empresarial reusable:

  KPI-101
  Aumentar ventas

  Puede contener nombre, código, descripción, familia y conocimiento conceptual.

  No contiene:

  - resultados históricos;
  - baselines;
  - Compliance;
  - Goal Met;
  - configuración específica de cada período.

  El usuario conserva siempre el control del nombre original.

  ### KPI Configuration

  Representa una forma operativa de utilizar una Definition.

  Puede establecer defaults como:

  - Behavior;
  - Measurement Unit;
  - Result Semantics;
  - Input Frequency;
  - Calculation Pattern;
  - Goal;
  - Comparison Mode;
  - reglas de evaluación aprobadas.

  No almacena resultados históricos.

  ### Calculation Pattern

  Describe exclusivamente cómo se obtiene Current Result.

  Valores conceptuales actuales:

  DIRECT
  DERIVED
  MULTI_INPUT_CURRENT_PERIOD
  COMPOSITE

  COMPARISON ya no es un Calculation Pattern.

  ### Comparison Mode

  Es una dimensión independiente del Calculation Pattern:

  NONE
  PREVIOUS_PERIOD
  SAME_PERIOD_PREVIOUS_YEAR
  CUSTOM_PERIOD

  Ejemplos:

  Sales:
  DIRECT + PREVIOUS_PERIOD

  ROA:
  DERIVED + SAME_PERIOD_PREVIOUS_YEAR

  ### Behavior

  Describe la dirección favorable de la métrica empresarial evaluada:

  Sales USD
  → GREATER_IS_BETTER

  Cost USD/KM
  → LOWER_IS_BETTER

  Incidents COUNT
  → ZERO_IS_BETTER

  No describe el Compliance ni debe inferirse únicamente a partir de palabras como “aumentar” o “reducir”.

  ### Comparison Direction

  Es independiente de Behavior:

  INCREASE
  REDUCTION

  Ejemplo:

  Reducir costo por KM 10%

  Behavior:
  LOWER_IS_BETTER

  Comparison Direction:
  REDUCTION

  ### Unidades y resultados derivados

  Los valores empresariales deben conservar su unidad real:

  Current Result → USD
  Baseline → USD
  Target Value → USD
  Derived Change → %
  Compliance → %

  Un Goal del 10% no convierte la Measurement Unit del KPI en porcentaje.

  ### Pool

  El Pool proporciona contexto temporal y operativo.

  Puede establecer valores efectivos sobre defaults de Configuration, incluyendo conceptualmente:

  - Goal;
  - Comparison Mode.

  Estos overrides solo pueden existir cuando el negocio los permita.

  ### Scorecard y FINALIZED

  El Scorecard:

  - selecciona Configurations del Pool;
  - asigna Weight;
  - construye una composición;
  - congela la configuración efectiva al finalizar.

  Después de FINALIZED, los cambios en Definition, Configuration o Pool no deben afectar el Scorecard histórico.

  ### Frozen Snapshot

  Preserva las instrucciones exactas necesarias para evaluar el KPI tal como estaban al finalizar:

  - identidad;
  - revisión de Configuration;
  - nombre vigente;
  - Behavior;
  - unidad;
  - semántica;
  - Calculation Pattern;
  - frecuencia;
  - Effective Goal;
  - Comparison Mode;
  - Weight;
  - scoring y thresholds aplicables;
  - procedencia relevante.

  No es el Monitoring Result y no contiene razonamiento del Analyzer.

  ### Monitoring

  Monitoring trabaja con el Frozen Snapshot.

  Es responsable de:

  - Current Results;
  - resolución del período requerido;
  - baselines;
  - Baseline Source;
  - resultados derivados;
  - Compliance;
  - Goal Met;
  - validación y cierre.

  Monitoring nunca analiza el KPI Name.

  ### Baseline Resolution

  La prioridad conceptual quedó definida:

  1. SELF_HISTORY
  2. MAPPED_KPI_CONFIGURATION aprobado
  3. MANUAL
  4. BASELINE_MISSING

  Reglas firmes:

  Missing baseline ≠ 0

  Baseline = 0 como denominador
  → INVALID_BASELINE

  Sin baseline válido
  → WAITING_FOR_BASELINE
  → Compliance = null
  → Goal Met = null

  ### Historical Mapping

  El mapping debe establecerse principalmente entre KPI Configurations concretas:

  KPC-205-01
  → KPC-088-02

  La similitud puede sugerir un mapping, pero nunca aprobarlo.

  Family y Unit compatibles no son evidencia suficiente de equivalencia empresarial.

  ### Refresh Baseline

  Refresh:

  - busca historia propia;
  - después mappings aprobados;
  - mantiene missing si no encuentra algo compatible;
  - no elige cualquier KPI parecido;
  - no reemplaza silenciosamente un baseline manual.

  ### Períodos cerrados

  Un Monitoring Period CLOSED debe preservar:

  - baseline utilizado;
  - valor utilizado;
  - período resuelto;
  - procedencia;
  - evaluación histórica.

  Una corrección posterior del resultado fuente no debe recalcular silenciosamente un período cerrado.

  ### Compliance para el caso confirmado

  Para un KPI comparativo con Target Value:

  Compliance Rate =
  Current Result / Target Value × 100

  Ejemplo:

  Baseline = 100,000
  Goal = +10%
  Target = 110,000
  Current = 105,000

  Compliance = 95.45%
  Goal Met = false

  No se utiliza:

  Achieved Change / Target Change

  Compliance puede superar 100% y no tiene cap por ahora.

  ### Goal Met confirmado

  Tiene tres estados:

  true  → ✅
  false → ❌
  null  → —

  Para GREATER_IS_BETTER:

  goalMet = Current Result >= Target Value

  null significa que todavía no puede evaluarse.

  ## 2. Dudas funcionales abiertas

  ### Target de reducción

  Falta confirmar si una reducción se traduce oficialmente como:

  Target Value = Baseline × (1 − Goal)

  También falta definir cómo se representa el Goal internamente:

  10
  10%
  0.10
  +10%
  -10%

  ### Compliance para otros Behaviors

  No están definidas las fórmulas para:

  LOWER_IS_BETTER
  ZERO_IS_BETTER
  RANGE
  EQUAL_IS_BETTER
  BINARY
  MILESTONE

  Tampoco sus reglas de goalMet.

  ### Valores cero o negativos

  Falta definir:

  - Target igual a cero.
  - Target negativo.
  - Baseline negativo.
  - Current Result negativo.
  - Reducciones superiores al 100%.
  - Casos financieros donde valores negativos puedan ser válidos.

  ### Rounding

  No están definidos:

  - escala decimal;
  - cuándo redondear;
  - modo de redondeo;
  - precisión de almacenamiento;
  - precisión presentada en UI;
  - si los cálculos encadenados usan valores redondeados o completos.

  ### Caps de Compliance

  Está confirmado que no se aplicará cap por ahora, pero sigue abierta la regla futura:

  - si alguna familia tendrá cap;
  - si será global o configurable;
  - si afectará Compliance, Weighted Contribution o solamente presentación.

  ### Traffic Lights

  Falta definir:

  - si se aplican sobre Compliance;
  - si pueden usar otra métrica;
  - cómo funcionan con Compliance superior a 100%;
  - cómo se comportan cuando la evaluación es null;
  - su relación con Goal Met.

  ### CUSTOM_PERIOD

  Falta determinar si representa:

  - un período único;
  - un rango;
  - un promedio;
  - una suma;
  - un valor de cierre;
  - otro agregado.

  También falta definir cómo se valida su compatibilidad temporal.

  ### MULTI_INPUT_CURRENT_PERIOD

  Si no existe fórmula oficial, no está definido:

  - si hay un Current Result principal;
  - si se conservan únicamente inputs separados;
  - si la Configuration queda bloqueada;
  - si puede llegar a Monitoring;
  - cómo se evalúa.

  ### COMPOSITE

  Se sabe que requiere fórmula y pesos oficiales, pero no están definidos:

  - estructura de componentes;
  - reglas de pesos;
  - versionamiento;
  - evaluación;
  - tratamiento de inputs faltantes.

  ### Baseline manual

  Falta definir:

  - quién puede ingresarlo;
  - quién lo aprueba;
  - evidencia obligatoria;
  - razón requerida;
  - posibilidad de edición;
  - auditoría;
  - tratamiento después de Submit, Validate o Close.

  ### Refresh sobre baseline manual

  Está claro que no puede reemplazarlo silenciosamente, pero falta definir:

  - qué comparación muestra;
  - quién autoriza el reemplazo;
  - si conserva ambas versiones;
  - si invalida la evaluación;
  - si requiere una razón.

  ### Historical mappings

  Falta definir:

  - aprobador;
  - vigencia;
  - versionamiento;
  - alcance global o por Pool;
  - alcance por organización o scope;
  - revocación;
  - auditoría;
  - compatibilidad exacta.

  ### Correcciones históricas

  Mientras Monitoring está abierto, falta definir qué ocurre si Refresh encuentra un valor fuente corregido:

  - si la evaluación pasa a STALE;
  - si se requiere Check Results;
  - qué ocurre en SUBMITTED;
  - qué ocurre en VALIDATED;
  - desde qué estado ya no se permite actualizar.

  ## 3. Inseguridades conceptuales controladas

  No son contradicciones, pero requieren precisión antes del diseño.

  ### Significado exacto de DIRECT

  Debe aclararse si DIRECT significa exclusivamente que el usuario ingresa el valor o si también incluye valores obtenidos automáticamente desde EMS, ERP o API sin transformación.

  Una definición más estable podría ser:

  DIRECT = el KPI Result es el valor observado,
  sin fórmula de transformación de negocio

  La fuente de captura sería otra dimensión.

  ### Behavior en métricas comparativas

  Está confirmado que Behavior describe la métrica empresarial. Sin embargo, debe asegurarse que toda evaluación comparativa aplique coherentemente:

  Behavior → Current/Target
  Comparison Direction → construcción del Target

  Especialmente para reducción y valores negativos.

  ### Comparison Mode frente a Comparison Direction

  Parecen dimensiones independientes:

  Comparison Mode
  → qué referencia usar

  Comparison Direction
  → qué tipo de cambio se persigue

  Falta confirmar si Comparison Direction siempre es obligatorio cuando Mode no es NONE, o si puede derivarse de Behavior en algunos casos.

  ### Definition frente a scope

  La referencia indica que ubicación, flota y operación normalmente pertenecen a Configuration. Aún falta una regla empresarial precisa para saber cuándo el scope cambia tanto el
  concepto que justifica otra Definition.

  ### Frozen Snapshot frente a evaluación congelada

  Se distinguen conceptualmente:

  FINALIZED
  → congela configuración operativa

  CLOSED
  → congela evaluación, resultado y baseline utilizados

  Falta confirmar si serán dos snapshots diferentes o una evolución versionada del mismo agregado. No debe decidirse todavía físicamente.
